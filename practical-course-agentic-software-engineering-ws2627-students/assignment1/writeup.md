## Part V: Reflection

Before this experiment I imagined a coding agent as a chat with a smart model that "remembers" my project. The trace shows that nothing is remembered: each of the 19 requests is a separate, stateless POST that sends the full system prompt (8.5 KB in `system[2]`), 16 tool definitions and the whole conversation again. This is why the request body grew from about 110 KB (R03) to about 154 KB (R19).
What also surprised me is how much of the "user" side is not written by me. `messages[0]` contains two harness-written `<system-reminder>` blocks before my one sentence, tool results arrive with `role: "user"`, and even `role: "system"` messages appear inside `messages` as "Environment update" notes.

Comparing R16–R19 showed me how information is carried forward by appending. The system prompt and tools stayed identical, old messages were replayed word for word, and each step added just a `tool_use` and a `tool_result`. Nothing was summarized, even at 154 KB. My follow-up about the first changed file could be answered from history alone (the diff in `messages[18]`, the `Edit` in `messages[24]`), with no new tool call. The downside is that information read by the agent can remain in the conversation history and be transmitted again in subsequent requests.

Tools are the agent's connection to the project. The model never saw my broken file directly; it saw the output of a `git diff`. The `tool_use_id` links each call to its result, and the denied `git checkout` (`messages[21]`) showed that the harness can block a plan, after which the agent switched to `Read` and `Edit`. I also learned to separate "the tool ran" from "the tests passed". The first test run (`messages[8]`, `[10]`) returned valid output, but the repo was not yet broken, so the agent correctly said it could not reproduce the failure. Only the text `OK` told it anything about the tests.

One interesting observation from my experiment was that I initially edited the function without saving the file. As a result, the tests still passed because the agent was working with the unchanged version on disk. Once I saved my changes, the tests failed and the agent identified the problem through `git diff`. This taught me that an agent's view of the project depends on the information its tools can access, not necessarily what is currently visible in my editor.

In practice, I would give an agent a concrete failing command and a clear success criterion instead of "tests are failing", because it can only act on what is in its context. I would split work into small tasks whose history I can audit. I would also check the tool results myself and not rely only on the agent's summary (`messages[29]`), since that summary is the model's own claim about those results. Finally, I would keep secrets out of the working directory, because the trace proves that every file the agent reads is sent to the API again and again.
